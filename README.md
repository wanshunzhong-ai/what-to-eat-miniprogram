# 今天吃什么 🍽️

一个解决「一日三餐吃什么」的**微信小程序**：**定位识别城市 → 选人数 → 一键推荐**。
两条路可选：**🍳 自己做**（推荐一桌菜 + 做法）或 **🛵 点外卖**（推荐附近的店）。

> 纯微信小程序项目（WXML / WXSS / JS），并已接入**微信云开发（CloudBase）**：
> 推荐计算优先在云函数里执行，云端不可用时自动降级为本地同款逻辑，离线也能用。

## ✨ 功能

### 🍳 自己做

- **自动定位**：调用 GPS 拿到经纬度，自动匹配最近的城市（内置 130+ 城市坐标，无需任何地图 Key）
- **按城市推荐**：识别城市后，优先推荐当地菜系（成都→川菜、广州→粤菜、西安→西北菜…）
- **按人数配菜（照风俗习惯来，人数 15 人内）**：选完人数后当场给出**冷热菜配比建议**（凉菜 / 荤 / 素 / 汤 / 主食各几道），食材用量同步按人数换算（如「嫩豆腐 450 g」）。人数 1~15 都可选，快捷选项 1~15 人，也可用「＋ / −」步进器微调
- **智能搭配**：一桌菜自动保证荤 / 素 / 汤 / 主食的搭配，不重复、不翻车；本地菜系优先，缺项才用家常菜兜底
- **口味偏好（推荐的两大依据之一）**：辣度（随便 / 不吃辣 / 微辣 / 中辣 / 重辣）、是否清淡。
  - 推荐只按 **人数 + 口味** 来配：**人数**决定一桌的结构（几凉几热、荤素汤饭怎么搭），**口味**决定从各分类里挑哪几道菜
  - 辣度是硬约束（选「不吃辣」就不会出现辣菜）+ 软加权（越贴近所选辣度越优先）；点「中辣 / 重辣」时，本地口味偏清淡的城市也会按口味翻出辣菜来
  - 「想清淡」会优待清淡做法（少辣、素 / 汤 / 凉菜 / 轻食），重口菜降权
- **做菜时间不设限**：菜品不分快手 / 慢炖，全凭菜系与口味挑，结果页只作「其中最费时的一道约 X 分钟」的参考展示
- **换一批**：不满意就一键换一批
- **菜品详情**：食材清单（按人数换算）、做法步骤、小贴士，可收藏
- **菜品库调用式，不内嵌**：菜品库放在云端，运行时由 `dishes` 云函数下发（云端 → 本地缓存 → 内置兜底三级降级）。
  **加菜 / 改菜不用改代码、不用重新发版**，改完云端数据下次进入即生效；「我的」页可查看菜品库来源 / 版本 / 数量并手动更新。

### 配比规则（中式用饭惯例，非硬性规定）

| 人数 | 凉菜 | 热菜 | 汤 | 主食 | 依据 |
|---|---|---|---|---|---|
| 1–2 人 | 0 | 2（荤素相当） | 0 | 1 | 人少不上凉菜，清爽不浪费 |
| 3–5 人 | 1–2 | 3–5（荤略多于素） | 1 | 1 | 「一人一热菜」的家常习惯 |
| 6–10 人 | 2–3 | 6–10（荤约为素的 1.5 倍） | 1 | 1 | 待客「N 菜一汤」 |
| 11–12 人 | 4（四冷盘封顶） | 11–12 | 2 | 2 | 宴席规格，双汤双主食 |
| 13–15 人 | 4 | 13–15（一人一热菜，封顶 15） | 2 | 2 | 十五人大席，一桌摆开 |

> 冷盘最多 4 道（传统「四冷盘」即上限）；热菜按「一人一道」最高 15 道（人数上限 15，再多就该分两桌）。早餐不讲冷热配比，以**主食 + 小吃**为主，人多再加轻食 / 汤。

### 🛵 点外卖

- **附近的真实店铺**：定位后列出你周围的餐馆，显示**店名 / 距离 / 地址 / 电话**
- **品类筛选**：全部 / 早餐 / 快餐简餐 / 面食米线 / 盖饭套餐 / 小吃 / 家常炒菜 / 火锅 / 烧烤烤肉 / 甜品饮品 / 西餐 / 日料 / 韩餐
- **按「人数 + 预算」排序**：一个人更适合单份快餐，人多更推火锅烤肉；预算档位（20 元内 / 20-50 / 50-100 / 100+）只改排序，不重新请求
- **一键导航 / 打电话 / 复制地址**：导航打不开时自动退化为复制地址
- **店铺收藏**：喜欢的店收藏起来，下次直接看
- **配送参考（估算）**：每家店显示**人气参考 / 起送价 / 配送费 / 预计送达**，
  超出常规配送半径的会标出来，单人凑不满起送价也会提醒
- **兜底**：没配置地图 Key 或网络失败时，不会白屏——给出明确提示与当地人气美食指引

> ⚠️ 配送那几项是**估算**，不是平台报价：地图接口（腾讯位置服务 / OpenStreetMap）**不返回**
> 起送价、配送费、时效和评分，这些只有美团 / 饿了么的开放平台才有。做法是「先按品类给区间，
> 再用店铺 id 的稳定哈希在区间内取值」——同一家店每次看到的数字都一样，不会乱跳。
> 页面上已明确标注，想换成真实数据只需在 `utils/takeout.js` 的 `decorateShop` 里覆盖这几个字段。

### 通用

- **本地人气**：推荐该城市/菜系值得一吃的特色小吃
- **历史 & 收藏**：记录每次「自己做」和「点外卖」，带类型标签，可一键复现
- **☁️ 云端同步**：收藏 / 店铺收藏 / 使用历史 / 口味偏好按**微信身份**存在云端，
  **换手机、换设备登录同一个微信就自动恢复**；断网时照常可用，联网后自动补上
- **📋 点菜清单导出 & 分享**：结果页可**复制清单文本**、**存成一张清单图**，
  或**一键分享**——分享出去的是一条链接，朋友点开就能看到这一桌，不用截图

## 🎨 界面与设计系统

视觉方向是**清爽现代风**：中性灰阶打底，橙色只做「强调」，不做大面积铺色。全部样式收敛成
`app.wxss` 里的一套 token，页面里不再出现魔法色值和重复定义。

### 设计原则

1. **橙色只用于强调**——选中态 chip、主按钮、一处分区标题色条。其余全是中性灰
2. **白卡 + 1rpx 细描边 + 极浅阴影**，取代早期的重投影，观感更轻
3. **字号 / 圆角 / 阴影 / 间距全部 token 化**，跨页面一致
4. **可点即反馈**：所有可点元素都带 `hover-class` 按压态
5. **首屏分区依次淡入**（`anim-up` + `d1~d6` 延迟档），外卖加载态用**骨架屏**而不是转圈

## ☁️ 云开发（CloudBase）接入

### 它是怎么工作的

```
首页点「帮我决定」
      │
      ▼
utils/engine.js ──► 云函数 recommend（云端跑推荐逻辑）
      │                    │ 取菜品库
      │                    ▼
      │              云存储 dishlib/dishlib.json（加菜/改菜不用发版）
      │                    │ 成功
      │                    ▼
      │              返回一桌菜结果
      │
      └─ 未启用 / 初始化失败 / 调用失败 ──► 本地 utils/recommender.js（结果一致）
```

- 小程序启动时在 `app.js` 里 `wx.cloud.init({ env, traceUser: true })` 初始化一次。
- 推荐统一走 `utils/engine.js`：**云端优先，本地兜底**，任何一步失败都不会影响使用。
- 云端与本地复用**同一套** `recommender / cities / foodData`，结果一致；**菜品库是运行时注入的**，不在代码里内嵌。

### 菜品库：调用式，不内嵌

菜品库**不打包进小程序**，而是运行时「调用」云端数据：

```
小程序 utils/dishStore.js ──► 云函数 dishes ──► 云存储 dishlib/dishlib.json
        │  三级来源，逐级降级
        └─ cloud（云端最新） → cache（本地缓存，离线可用） → builtin（内置兜底 47 道，首次无网可用）
```

- **加菜 / 改菜不用改代码、不用重新发版**：更新云端数据即可，用户下次进入自动生效。
- 客户端带 `version` 比对，版本没变就不重传整库，省流量。
- 云函数 `dishes` 的 `action`：`list`（取库，默认）/ `get`（取单菜）/ `meta`（版本与分布）/ `publish`（热更新写回云存储）/ `seed`（把出厂数据集写回云存储）。
- 完整库的唯一数据源是仓库里的 `data/dishlib.json`（**已被 `packOptions.ignore` 排除，不进小程序包**），
  用 `node scripts/sync-dishlib.js` 校验并同步到 `cloudfunctions/dishes/dishlib.json`。
- 「我的」页可查看当前菜品库的来源 / 版本 / 数量，并可手动「更新菜品库」。

### ☁️ 用户数据云同步（换手机也不丢）

收藏、店铺收藏、使用历史、口味偏好都按**微信身份**存在云端，换设备登录同一个微信即自动恢复。

```
小程序 utils/userStore.js ──► 云函数 userdata ──► PostgreSQL 表 eat_user_data
        │  (纯传输层)                │  身份取自 cloud.getWXContext().OPENID
        │                            │  （前端不传 openid，用户之间天然隔离）
        └─ 断网 / 未配置 / 报错 ──► 静默退化为纯本地，功能不受影响
```

**离线优先**：本地写入永远立即生效、立刻落盘；同步在后台异步进行（改动后延迟 900ms 合并成一次请求）。

**冲突怎么解**：按「集合级时间戳」取更新的一方（last-write-wins）——
所以在手机上取消了收藏，另一台设备同步后也会跟着取消；某台旧设备送来的陈旧数据不会覆盖新数据。
四个集合（`pref` / `favorites` / `shopFavorites` / `history`）各自独立比时间戳，互不干扰。

| 位置 | 作用 |
|---|---|
| `utils/userStore.js` | 客户端同步层（纯传输 + 防抖排队，不碰本地缓存键） |
| `app.js` | `exportState()` / `importState()` / `bumpSync()`：本地状态的读、写、打时间戳 |
| `cloudfunctions/userdata/` | `pull` / `sync` / `clear` 三个动作，含合并逻辑 |
| `cloudfunctions/userdata/pgrest.js` | CloudBase PostgreSQL 的最小 REST 客户端 |
| `cloudbase/migrations/*.sql` | 建表迁移（`eat_user_data`，RLS 开启、无 policy，仅云函数可访问） |
| 「我的」页 | 云同步状态卡片 + 「立即同步」按钮 |

### 🎯 推荐云函数按 OPENID 做个性化

`recommend` 云函数会按 OPENID 记住口味偏好（存在同一张 `eat_user_data` 表里）：

- 客户端这次带了**有效偏好** → 用它，并在后台把口味记到云端；
- 客户端这次**没带**（比如换了手机、本地还没恢复）→ 用云端记着的那个。

返回值里有 `prefUsed`（实际用的口味）和 `prefSource`（`client` / `cloud` / `none`），便于排查。
写入走**读-改-写且比时间戳**，只动 `pref` 两个键，不会碰到收藏和历史；同容器内另有 60 秒短缓存，连推几桌不重复查库。

| 动作 | 实现 |

分享链接怎么带的菜单？**菜名直接编码进 `path`**（`/pages/share/share?m=...`），

真超了（> 700 字符）会自动退化成普通分享，不会给出一条打不开的链接。

### 运行环境兼容（`utils/wxapi.js`）

不同运行环境实现的 `wx` 接口并不一致——真机、开发者工具、**预览沙箱**之间都有差异。
例如预览环境没有实现 `wx.getLocation`，若直接调用会抛 `wx.getLocation is not a function`，
`onShow` 等生命周期会被这个异常打断，页面看起来就像"没跑起来"。

因此 `app.js` 启动时会调用 `wxapi.install()`，做两件事：

- **缺失接口兜底**：对 `showToast / showModal / navigateTo / pageScrollTo` 等非关键接口，
  缺失时补一个安全实现（真机上这些接口都存在，不会被替换，行为完全不变）；
  同步存储缺失时用内存实现兜底，预览环境里收藏/历史依然可用。
- **定位走安全层**：定位统一调用 `wxapi.getLocation()`（Promise 版，**绝不抛异常**），
  依次尝试 `getLocation` → `getFuzzyLocation`，都没有时返回"环境不支持"，
  页面改为提示手动选城市（预览环境会默认取一个人气城市并明确提示，保证功能可用）。

> 结论：**不要再在页面里裸调 `wx.getLocation`**，请统一用 `wxapi.getLocation()`。

### 定位精度策略（`wxapi.getLocation` + `cities.findNearest`）

识别城市准不准，取决于「设备给的坐标准不准」和「匹配算法准不准」两段，这里两段都做了处理：

**第一段 · 拿到尽量准的坐标**（`wxapi.getLocation`）

| 做法 | 说明 |
|---|---|
| 开启高精度 | `isHighAccuracy: true` + `highAccuracyExpireTime: 8000`。**不要关掉**——关掉后微信只给基站/网络级位置，偏差常见几百米到几公里 |
| 多次采样取最优 | 精度 > 50m 时自动再采一次，取 `accuracy` 最小的一次（最多 2 次） |
| 短时快照复用 | 2 分钟内的定位结果直接复用，避免刚定位完又被降级成粗略值 |
| 精度可见 | 结果带 `accuracy`（米），首页会显示「精度约 ±35 米」，模糊定位会显示「±2 公里（较粗略）」 |
| 强制重新定位 | 「🎯 重新定位」按钮传 `fresh: true`，跳过快照 |

**第二段 · 匹配置信度**（`utils/cities.js`）

- **131 座城市**（地级市为主），覆盖全国；`findCandidates()` 按距离升序返回候选。
- **直辖市多锚点**：北京/上海/天津/重庆辖区跨度数百公里，单点中心会把远郊区县判给隔壁城市
  （如「重庆万州」曾匹配到南充）。这些城市带 `anchors` 数组，匹配时取「市中心 + 各锚点」的最近距离。
- **跨界不瞎猜**：最近的两座城市距离相差 < 25km **且菜系不同**时，标记 `ambiguous`，
  首页弹候选让用户点一下确认（同菜系的相邻城市不打扰用户）。
- **附近无收录城市**：最近城市 > 150km 时标记 `lowConfidence`，首页明说「已按最近的 X 推荐，相距约 N 公里」。
- **「离你最近」列表**：城市选择页会按定位距离列出最近 6 座城市（带公里数），识别不准可直接点选更正。

### 部署云函数

四个云函数**均已部署到环境 `zws-04161130-l`**，调用验证通过：

| 云函数 | 作用 | 备注 |
|---|---|---|
| `dishes` | 菜品库下发 + 热更新 | 已播种云存储 `dishlib/dishlib.json`（341 道，v2026.10.10.1） |
| `recommend` | 推荐一桌菜 | 运行时从云存储取菜品库（返回 `source: "cloud"`）；按 OPENID 读口味做个性化 |
| `nearby` | 附近美食店 | 双数据源：配了 `TENCENT_LBS_KEY` 走腾讯位置服务，否则走 OpenStreetMap（免密钥） |
| `userdata` | 用户数据云同步 | 按 OPENID 读写 PG 表 `eat_user_data`，需环境变量 `CLOUDBASE_APIKEY` |

`dishes` / `recommend` 都建议配置环境变量 `DISHLIB_FILE_ID`（菜品库在云存储里的 fileID），
`recommend` 会优先直连云存储取库，少一跳、更快。

> ⚠️ `userdata` 与 `recommend` 需要环境变量 **`CLOUDBASE_APIKEY`**（服务端 API Key，`service_role`）。
> 这是**云函数访问 PostgreSQL 的唯一通道**：云函数内 `app.rdb()` 不可用（会报 `DATABASE_PGRST106`），
> 可行路径只有 `https://<envId>.api.tcloudbasegateway.com/v1/rdb/rest/<table>`（Bearer API Key）。
> Key 在 CloudBase 控制台「环境 → 登录授权 / API Key」创建，**只配在云函数环境变量里，绝不下发前端**。
> 表结构迁移在 `cloudbase/migrations/`，用 `managePgDatabase(action=applyMigration)` 应用。


若你更换了环境，或修改了 `cloudfunctions/` 下的数据/逻辑需要重新上传：

1. 微信开发者工具顶部点「**云开发**」，用**微信公众平台登录**，确认能看到环境 `zws-04161130-l`（看不到见下方排查）。
2. 在左侧文件树找到 `cloudfunctions/dishes` 与 `cloudfunctions/recommend` → 分别 **右键 → 「上传并部署：云端安装依赖」**。
3. 首次部署 `dishes` 后，调一次 `{"action":"seed"}` 把菜品库写入云存储（之后改菜走 `publish` 即可）。
4. 等编译完成，回到首页点「帮我决定」。若控制台打印 `[云开发] 初始化完成` 且结果正常，说明云端已生效。

> 想验证走的是云端还是本地：结果对象里有 `source` 字段，`cloud` 表示云端、`local` 表示本地兜底。
> 推荐结果里还会带 `dishLibVersion` / `dishLibCount`，用来确认菜品库确实是运行时取到的。
> 「点外卖」那条路必有 `source: 'cloud'`——附近的店没有本地等价实现，必须联网。

## 🛵 附近店铺（双数据源：不配 Key 也能用）

「点外卖」要列出**你附近的真实店铺**。`nearby` 云函数内置**两路数据源**，自动降级：

```
pages/takeout ──► utils/engine.js ──► 云函数 nearby ──┬─► 1) 腾讯位置服务 周边搜索（配了 Key 时优先，最准，带电话）
                                                      └─► 2) OpenStreetMap Overpass（免密钥兜底，永远可用）
    └─ 拿不到位置 / 两路都失败 ──► 说清原因的提示卡 + 当地人气美食兜底（不留死路）
```

| 数据源 | 需要 Key | 数据质量 | 何时生效 |
|---|---|---|---|
| **腾讯位置服务** | 需要（`TENCENT_LBS_KEY`） | 最全：分类、电话、精确距离，全国覆盖 | 配了 Key 就优先走它 |
| **OpenStreetMap** | **不需要** | 大城市够用（北京/成都 3km 内 70~100 家），**中小城市覆盖有限** | 没配 Key，或腾讯侧失败时自动启用 |

结果页会标注数据来源（`数据来自腾讯地图` / `数据来自 OpenStreetMap`）。

**Key 为什么放在云函数里？**

1. Key 是敏感凭证，放云函数**环境变量**里不会下发到小程序前端；
2. 云函数出网不受小程序「request 合法域名」白名单限制，**省去后台配置**；
3. 上游错误码可以在服务端统一翻译成人话再给前端（如「IP 未授权」「Key 未开通 WebServiceAPI」）。

### （可选，推荐）申请并使用腾讯地图 Key（约 3 分钟）

不配也能用，但配了门店更全、还能显示电话：

1. 打开 [腾讯位置服务控制台](https://lbs.qq.com/dev/console/key/manage)（用微信/QQ 登录），
   进入「**应用管理 → 我的应用**」→ **创建应用** → 在应用下 **添加 Key**。
2. 添加 Key 时**务必勾选「WebServiceAPI」**（周边搜索属于 WebService 能力），
   IP 限制可先留空（不限 IP）。
3. 复制这串 Key，在云开发控制台（或 CloudBase 控制台）配置 `nearby` 的环境变量：

   | 变量名 | 值 |
   |---|---|
   | `TENCENT_LBS_KEY` | 你刚申请的 Key |
   | `OSM_ENDPOINT`（可选） | 想指定 Overpass 镜像时填，如 `overpass-api.de` |

4. 重新部署 `cloudfunctions/nearby`（改了环境变量后建议重发一次）。

> **别把 Key 写进小程序代码**——前端能反编译出来。也不建议在小程序里直连地图 API：
> 小程序 request 有「合法域名」白名单限制，还会把 Key 暴露在网络上。

### 常见提示对照

| 现象（外卖页提示） | 原因 | 处理 |
|---|---|---|
| 📡 云函数没调通 | `wx.cloud.callFunction` 失败：预览面板不支持云调用 / 云环境未绑定当前小程序 / 网络不通 | **用微信开发者工具打开本项目**（或真机）再试；确认 AppID 已绑定该云环境 |
| 🔑 地图 Key 没生效 | `TENCENT_LBS_KEY` 为空或 Key 未开通 WebServiceAPI | 按上面步骤配置；只影响「更精准」这一层，此时会自动退回 OpenStreetMap |
| ⏳ 地图服务额度用完了 | 腾讯侧调用量/并发达上限 | 控制台查看配额，或次日再试 |
| 🌐 开源地图暂时不可用 | Overpass 被限流（短时间请求过多） | 稍后重试 |
| 页面提示「这一片没找到符合条件的店」 | 当前品类 + 半径内确实没有 | 换品类、点「重新找找」，或看看下方人气美食 |

> **重要**：`wx.cloud.callFunction` 必须在**支持云开发的环境**里运行。WorkBuddy 右侧的
> 「预览面板」是能力不完整的模拟器（不提供真实定位、也不提供云调用），
> 要验证「附近门店」请在**微信开发者工具**中打开本项目。

> 半径默认 3 公里（`config.js` 的 `NEARBY_RADIUS`），搜索时带「结果不足自动向外扩展」标记，所以不必设太大。
> 地图接口**不返回价格**，页面上的「参考人均」是按品类给出的经验区间，属于估算，已以「参考人均」字样标注以免误导。

## 🛠️ 如何扩充

- **加菜 / 改菜（推荐，不用发版）**：改 `data/dishlib.json` → 跑 `node scripts/sync-dishlib.js` → 重新部署 `dishes` 云函数；
  或者直接调 `dishes` 云函数的 `publish` 动作把新库写进云存储，用户下次进入即生效
- **调整内置兜底**：改完 `data/dishlib.json` 后跑 `node scripts/gen-fallback.js` 重新生成 `utils/dishes.js`
- **加城市**：在 `utils/cities.js` 的 `CITIES` 里加一行（名称、省份、经纬度、菜系）
- **加本地美食**：在 `utils/foodData.js` 里补充
- **加外卖品类**：在 `utils/takeout.js` 的 `CATEGORIES` 里加一项，并在 `CAT_RULES` 里补上识别关键词

改完 `cities.js / foodData.js / recommender.js` 后，把对应文件同步复制到 `cloudfunctions/recommend/`，
再在开发者工具里重新上传该云函数（`dishes` 云函数的菜品数据不需要复制到 `recommend`）。
